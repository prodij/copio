## Vision

### The 10x check (where we're going)

A category-defining product: **the executive assistant to the CEO of an Amazon-native e-commerce business**. Not a dashboard. Not a sync tool. A colleague.

The buyer hires it the way they'd hire a chief of staff: someone who reads everything overnight, has a point of view, tells the truth, gets sharper every week, and writes — actual prose, with citations, with confidence levels, with a voice. It already knows what's important. It quotes the CEO back to themselves when it's relevant. It says "I might be wrong" when it might be wrong. It learns when not to brief — launch week, weekend, the kid's birthday. It is the most opinionated piece of software the CEO uses.

The MVP scope is one capability of that vision: **diagnostic on demand**. *"Why is X happening with my Amazon business?"* answered with a written causal narrative + linked evidence, in <90 seconds, calibrated for honesty.

The two-stage MVP is deliberate: Phase 1.0 is a working dogfood internally, generating real diagnostics against the founder's own Amazon business, in days. Phase 1.1 is the productized version safe to put in front of paying customers. Compressing them into one 4-5 day shippable would mean cutting either the eval rig (kills the brand promise) or multi-tenancy (eats a painful retrofit later) — both unacceptable. Splitting them lets each be done at quality.

### Why this works (the strategic claim)

Amazon's March 2026 AI Agent Policy redefined the surface area:
- All SP-API automation must use official endpoints + audit logs
- Tier 1 (read/sync) — minimal restrictions
- Tier 2 (catalog/bid) — rate-limit + audit
- Tier 3 (high-impact) — human authorization required

Every legacy ERP (Veeqo, Sellbrite, Linnworks, ChannelAdvisor, SoStocked, Inventory Planner) is now retrofitting "agents" onto polling-era architectures designed before the policy existed. **Copio is being built agent-native from the first commit, on the first day after the policy that makes agent-native the only legal long-term path.** That timing is the wedge.

The MVP scope (Tier 1 only — read-only diagnostic) means we ship with **zero T2/T3 compliance burden**. We earn trust on writing, then earn the right to write actions in Phase 2.

## Accepted Scope — Phase 1.0 (dogfood, ~4-5 CC days)

Single-tenant against the founder's own Nutragroup Amazon account. Shipped to nobody but the founder.

- FastAPI + Postgres backend, **single-tenant** (skip RLS, KMS, audit chain at this stage)
- LWA OAuth flow for the founder's own SP-API access
- SP-API integration: **Orders + FBA Inventory + Reports (polling/scheduled-fetch)** — see SP-API Integration Reality below
- Diagnostic agent runtime: Sonnet 4.6 default, Opus 4.7 fallback, prompt caching on
- Tool palette: structured SP-API tool calls, math/stat tools, simple file-based memory
- **20 golden questions** authored by founder; manual judge runs (script, not nightly cron)
- **Unnamed "honest voice"** system prompt — uncertainty markers, "I can see" vs "I infer," apologizes when wrong
- Web chat UI (Next.js, streaming, citation overlay) — no auth, single user
- Audit log to local Postgres table (no checksum chain yet)
- 3 worked examples in `docs/EXAMPLES.md` showing good vs bad diagnostics in honest voice — written before the agent runs, used as runtime style anchor

## Accepted Scope — Phase 1.1 (productized, Week 2-4 in CC time, ~3 weeks human time)

The version safe to put in front of paying customers.

- **Audit `.deprecated/api/` first** to confirm what lifts cleanly. If <70% lifts, fall back to single-tenant for Phase 1.1 and revisit multi-tenancy in Phase 2.
- Multi-tenant: Postgres row-level security with `tenant_id = current_setting('app.tenant_id')`, KMS-encrypted LWA tokens, audit log with checksum chain, per-tenant prompt construction, per-tenant rate + cost budgets

- **Reaction pipeline**: thumbs/emoji on web chat → eval signal (👍 = gold candidate, 👎 = flag for review, free-text "tell me what was wrong" → tuning signal)
- Cross-tenant isolation: DB-level RLS + application-level assertion in `Memory.write` + integration test attempting cross-tenant write
- **Cross-tenant contamination eval**: sentinel-string probes nightly + unit test on prompt builder
- **Eval-rig health observability**: judge variance check (same answer × 5 runs/week, alert on stdev > 0.5), nightly run completion rate, golden set growth
- Onboarding wizard: LWA OAuth, first diagnostic in 4-24h depending on report types (FBA/Orders are near-real-time; Brand Analytics + SQP take a backfill window)
- Slack bot **deferred to Phase 1.5** (see Long-Term Trajectory) — keeps Phase 1.1 to one OAuth flow and one surface
- Sandbox tenant for smoke tests (synthetic SP-API mocks); founder's Nutragroup is a weekly canary, not per-deploy
- Pricing: $199-499/mo (validation milestone listed in Risks)

## SP-API Integration Reality (corrects an earlier mis-claim)

Amazon's "event-driven cuts cost 80-90% vs polling" applies to a **subset** of resources. The product depends on a mix:

| Dataset | Mode | Latency |
|---|---|---|
| Orders | Event-driven (Notifications API: `ORDER_CHANGE`) | Real-time |
| FBA inventory | Event-driven (`FBA_OUTBOUND_SHIPMENT_STATUS`, `FBA_INVENTORY_AVAILABILITY_CHANGES`) | Real-time |
| Listing changes | Event-driven (`LISTINGS_ITEM_STATUS_CHANGE`) | Real-time |
| **Brand Analytics** | **Pull/Reports (scheduled)** | **Daily-weekly** |
| **Search Query Performance** | **Pull/Reports (scheduled)** | **Weekly** |
| **Selling Partner Reports** | **Pull/Reports (scheduled, request-poll-download)** | **15-60 min per report** |

The diagnostic agent depends heavily on the pull/report APIs (Brand Analytics, SQP, sales-and-traffic reports). Event-driven is used for inventory/order anomalies; pull is the dominant pattern for the questions the diagnostic actually answers. Cost optimization comes from caching report results aggressively (15-min TTL on hot, 24h on cold), not from webhooks alone.

### Diagnostic data flow (the happy path)

```
CEO asks: "Why are conversions down on SKU-A?"  (web chat / Slack)
   |
   v
[1] Tenant + memory loaded
    - LWA token decrypted
    - Per-tenant business context (categories, margin shape, prior decisions)
    - CEO preferences ("user said: don't suggest Walmart")
   |
   v
[2] Agent plans tool calls (Sonnet 4.6, streaming)
    - Hypothesis tree: traffic? listing? price? competition? ad spend?
    - Selects SP-API endpoints to query in parallel
   |
   v
[3] Tool calls (parallel, with cache layer)
    - Brand Analytics: search-term performance for SKU-A
    - Sales-and-traffic report: 30-day daily
    - Search Query Performance: impression / click / purchase share
    - Inventory: stock level + replenishment lead time
    - Cache: same (tenant, query, day) returns cached
   |
   v
[4] Causal decomposition
    - Sonnet 4.6 default; auto-escalates to Opus 4.7 if reasoning depth needed
    - Marks claims as "I can see" (cited) vs "I infer" (uncertainty quantified)
   |
   v
[5] Narrative drafted with honest voice prompt
    - Plain prose, not bullet soup
    - Every quantitative claim links to source data
    - "I'm 70% on this" / "I might be wrong about X"
    - Persona voice
   |
   v
[6] Streamed to CEO; full transcript persisted to audit log
   |
   v
[7] CEO reaction (thumbs / emoji / reply) -->
    - Eval set update
    - Memory update (CEO preference inferred)
    - Voice-consistency check
```

### Shadow paths

- **Nil input**: CEO question is empty / unparseable → agent asks one clarifying question, doesn't guess.
- **Empty data**: New seller, no Brand Analytics yet → agent says: "You're new — I don't have enough history to diagnose this. Come back in 7 days, or ask me about something where I have data: [list]." Never pretends.
- **Stale cache**: data is >24h old → agent says: "The latest data I have is from yesterday close. Want me to refresh?" Never silently stale.
- **Upstream error**: SP-API returns 503 / malformed JSON → log to audit, attempt fallback to cached, mark in narrative: "Brand Analytics is unavailable right now — here's what I can say from the rest." Never silently incomplete.

### State machine — diagnostic lifecycle

```
  [QUEUED]
     |
     | (worker picks up)
     v
  [PLANNING]            -- (tenant context load fails) -->  [FAILED_INTERNAL]
     |
     | (plan accepted)
     v
  [TOOL_CALLS]          -- (all tool calls fail)  -->       [FAILED_NO_DATA]
     |                                                              |
     | (some/all tool                                                | (no useful data
     |  calls succeed)                                               |  to draft against)
     |                  -- (>=1 tool fails) -->     [DEGRADED] ------+
     |                                                  |
     v                                                  v
  [REASONING]   ---------------------------------->  [DRAFTING]
     |                                                  |
     | (reasoning complete)                             | (degraded note included)
     v                                                  v
  [DRAFTING]    --------------------------->     [STREAMING]
                       (single path)
                                                        |
                                                        | (stream completes)
                                                        v
                                                  [COMPLETE]
                                                        |
                                                        | (CEO reaction within 24h)
                                                        v
                                                  [EVAL_RECORDED]

  Terminal states: [COMPLETE], [EVAL_RECORDED], [FAILED_INTERNAL], [FAILED_NO_DATA]
```

Triggers are labeled on every transition. Invalid transitions (e.g., `[COMPLETE] → [PLANNING]`) are blocked at the orchestrator. Every state change persists to the audit log with timestamp + reason. `[FAILED_NO_DATA]` (all tool calls failed) returns to the CEO as: "I couldn't pull anything useful right now — Amazon SP-API is having issues. I'll retry in 5 minutes."

## Error & Rescue Map

| Method/codepath | What can go wrong | Exception | Rescued? | Action | User sees |
|---|---|---|---|---|---|
| `SPAPIClient.call` | 429 rate-limited | `SPAPIRateLimit` | Y | Backoff + retry up to 3x; if still failing, mark capability degraded | "Brand Analytics is rate-limited; using cached data from 2h ago" |
| `SPAPIClient.call` | LWA token expired | `SPAPIAuthExpired` | Y | Refresh via stored refresh-token; retry once | Nothing (transparent) |
| `SPAPIClient.call` | SP-API endpoint 503 | `SPAPIUpstreamDown` | Y | Fall back to last cached data; flag in narrative | "Sales-and-traffic is unavailable; here's what I can say from yesterday's snapshot" |
| `SPAPIClient.call` | Malformed JSON | `SPAPIBadResponse` | Y | Log full payload; fall back to cache | Same as above |
| `SPAPIClient.call` | Tenant lacks permission for endpoint | `SPAPIPermissionDenied` | Y | Mark capability unavailable for tenant; instruct CEO to grant scope | "I need access to Brand Analytics to answer this. Here's the 1-click grant link." |
| `LLMClient.complete` | Model timeout | `LLMTimeout` | Y | Return partial response with note + offer retry | "I was thinking too long; here's what I had. Want me to keep going?" |
| `LLMClient.complete` | Model refusal / safety block | `LLMRefused` | Y | Re-prompt with safer framing once; if still refused, escalate to admin | "I couldn't answer that one — opening a ticket with the team." |
| `LLMClient.complete` | Hallucinated number | (caught by eval, not runtime) | (eval) | Eval rig catches in regression; runtime marks uncertainty | If runtime: "I'm <70% on this number — please verify before acting" |
| `LLMClient.complete` | Token budget exceeded | `LLMBudgetExceeded` | Y | Truncate context using memory recency; retry | Nothing if successful; admin alert if persistent |
| `Memory.write` | Cross-tenant write detected | `TenantIsolationBreach` | Y | **Block the write, page on-call, audit incident** | Generic error to user; full incident response |
| `Memory.search` | Empty result | (not an error) | N/A | Agent acknowledges no prior context | "I don't have history on this yet — first time you've asked." |
| `SlackClient.post` | Slack API 429/down | `SlackUpstreamDown` | Y | Queue + retry; if persistent, email fallback with link to web | "Slack didn't accept my reply — emailed it instead." |
| `Database.query` | Connection pool exhausted | `DBPoolExhausted` | Y | Circuit breaker for 60s, return 503 with retry-after | "I'm catching up — try again in a minute." |
| `PromptInjection.scan` | Malicious instruction in SP-API listing title | `PromptInjectionDetected` | Y | Strip / wrap in escape marker; log to audit | Nothing (transparent); admin sees in audit |

**Critical rule**: NO `except Exception:` blocks. Every catch is for a named class. Every rescue either retries with backoff, degrades gracefully with a user-visible message, or re-raises with added context. "Swallow and continue" is forbidden.

## Security & Threat Model

| Threat | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Cross-tenant data leak via LLM context bleed | Med | Critical | Per-tenant prompt construction; tenant_id baked into every memory key; nightly contamination eval; runtime check on response references |
| Prompt injection via SP-API listing title / search term | High | High | Sanitize all SP-API data before LLM ingest; wrap user-supplied strings in `<untrusted>` markers in prompts; eval set includes injection probes |
| LWA token exfiltration | Low | Critical | KMS encrypt at rest; never log tokens; rotate on schedule; row-level access controls |
| SP-API quota exhaustion (DoS via expensive queries) | Med | High | Per-tenant rate limits; cost budget per tenant; alert on spend anomaly |
| Audit-log tampering | Low | High | Append-only table; checksum chain; off-host backup |
| Hallucinated number → CEO acts on it → real loss | High | High | Honest-voice prompt requires uncertainty markers on numerical claims; eval rig regression-tests numerical accuracy; audit log preserves source data |
| Slack OAuth token theft | Low | Med | Short-lived; refresh; revoke on suspicious activity |
| Insider exfil via god-mode admin | Low | Critical | Reuse prior `.deprecated/api/` god-mode audit log model; alert on bulk reads; quarterly access review |

## Test / Eval Review (the moat)

### Eval rig design

**Golden set** (target 100 questions at MVP, growing):
- Each entry: `(question, snapshot_data, expected_facts, forbidden_facts, narrative_properties)`
- `expected_facts`: e.g., "must mention ad spend dropped 40%"
- `forbidden_facts`: e.g., "must NOT mention competitors by name"
- `narrative_properties`: voice match, uncertainty markers present, citations present

**Judge model**: Opus 4.7. Scores answers 0-10 across:
- Factual correctness (claims match snapshot data)
- Causal narrative coherence (cause → effect chain holds)
- Voice match (named persona consistency)
- Uncertainty calibration (confidence markers on inferences)
- Honesty (no defensive softening)
- Citation completeness (every quantitative claim cited)

**Regression cadence**: nightly. Alert on any score drop >0.5 vs 7-day baseline.

**Live signal pipeline**:
- 👍 reaction → flag as gold-standard answer for that question type
- 👎 reaction → flag for review; if pattern emerges, add as new test case
- "more like this" / "less like this" → voice-tuning signal

**Cross-tenant safety eval**:
- Every nightly run includes contamination probes (tenant A asks question; eval verifies no tenant B data appears)

**Voice consistency eval**:
- Sample N diagnostics across tenants; judge model scores voice-match; alert on drift

### Test pyramid

- **Unit**: 200+ tests on tools, parsers, memory ops, prompt builders
- **Integration**: 50+ tests on SP-API client (mocked + sandbox), Slack client, eval pipeline
- **Eval (above)**: 100+ golden questions, nightly regression
- **End-to-end**: 10+ scripted CEO journeys (sign-up → connect → first diagnostic)
- **Chaos**: weekly fault injection (SP-API 503, LLM timeout, DB pool exhausted)

### What I'd ship at 2am on a Friday

- Eval score 8.5+/10 on golden set, no individual case below 7.0
- Cross-tenant contamination probe: zero hits in last 7 nightly runs
- p99 diagnostic latency < 90s
- Last 24h error rate < 0.5%

## Performance

- **Latency target**: first token <2s; full diagnostic <60s p50, <180s p99 (revised from earlier 90s — Brand Analytics + SQP report pulls dominate p99 and were under-budgeted in the first pass)
- **Fast path**: max 2 SP-API tool calls + Sonnet 4.6 only → target 30s
- **Deep path**: 4-6 SP-API calls + escalation to Opus 4.7 + report polling → target 60-180s, async-eligible (CEO can close the tab; result lands in chat history + email if >2 min)
- **Cost**: Sonnet 4.6 + Anthropic prompt caching cuts repeated-context cost ~80%; budget $0.40-1.50 per diagnostic at MVP volumes
- **Throughput**: 50 concurrent diagnostics per backend node initially; scale horizontally
- **SP-API event webhooks**: real cost savings on Orders + FBA inventory + Listings (real-time event flows). Reports/Brand Analytics/SQP are pull-based — caching is the cost lever there, not webhooks.
- **Cache layer**: `(tenant, query, day)` tuple → cached SP-API responses; 15-min TTL on hot data (Orders, FBA); 24h on cold reports (Brand Analytics, SQP)

## Observability

Per-tenant dashboard:
- # diagnostics today / 7d / 30d
- Avg latency, p50/p95/p99
- Eval score 7d trend
- Cost per diagnostic 7d trend
- Reaction signal: 👍 rate, 👎 rate, no-reaction rate

Per-diagnostic trace:
- Tool calls (which, how long, cost)
- Tokens (in / out / cached)
- Reasoning chain (admin-only "agent inner monologue" view)
- Sources cited
- Confidence levels claimed

Alerts:
- Eval score drop >0.5 vs 7-day baseline
- Cost per diagnostic >2x 7-day median
- Error rate >1% in any 5-min window
- Cross-tenant contamination probe hit (page on-call)
- LWA token refresh failure rate >2%
- Slack delivery failure spike (Phase 1.5+)

Eval-rig health observability (Phase 1.1):
- Nightly run completion rate (target 100%; alert on miss)
- Judge variance check: same answer × 5 runs/week, alert on stdev >0.5 (catches a silently broken or drifting judge model)
- Golden set growth rate (target +5-10/week from reaction pipeline)
- Voice-consistency drift: weekly sample, judge model scores against persona examples, alert on drift

Runbooks:
- "Eval score dropped" → check recent prompt changes, rollback if regression
- "SP-API 503 storm" → switch to cached-only mode, surface to CEOs as "Amazon is having issues"
- "Cross-tenant probe hit" → freeze writes, audit, do not unfreeze without root cause

## Deployment

- **Region**: us-east-1 (SP-API is region-bound for North America)
- **Stack**: FastAPI on Fly.io or Render; Postgres on Supabase or RDS; Redis on Upstash; pgvector on same Postgres instance
- **Migrations**: Alembic; zero-downtime ready
- **Feature flags**: per-tenant capability flags (e.g., turn on Brand Analytics integration tenant-by-tenant during MVP)
- **Prompt versioning**: every system prompt versioned; rollback to prior version in <60s
- **Rollback plan**: standard git revert + redeploy; DB migrations all reversible at MVP scope
- **Smoke tests**: post-deploy run against a **synthetic sandbox tenant** with mocked SP-API responses; the founder's Nutragroup account is a **weekly canary** (not per-deploy). Sandbox tenant prevents per-deploy cost burn + quota burn + memory pollution on real data.

### The strategic logic of Phase 2 (the multichannel-from-Amazon play)

Phase 2 is what Copio's prior code (`.deprecated/api/`) was *trying* to be — multi-marketplace inventory + listing + order management. The previous build failed because it was **feature-checklist competition** against incumbents (Veeqo, Sellbrite, Linnworks, ChannelAdvisor) on their own surface. Phase 2 of the new Copio wins on a different axis:

1. **Catalog source-of-truth claim**: Amazon listings carry the richest product data any seller maintains. Treat Amazon as canonical, and every other channel becomes a derived view. Incumbents treat each channel as independent — that's why their UX is dashboard-soup.
2. **Agent-native HITL replaces forms**: incumbents make you fill out per-channel forms. Copio drafts every channel listing from your Amazon catalog and asks for batch approval. 47 listings replicated to Walmart in one approval session, not 47 hours of form-filling.
3. **Trust earned in Phase 1 cashes in here**: by Phase 2 the agent has a track record of honest diagnostics. CEOs trust it enough to let it draft listings against their entire catalog. That trust is unforgeable by incumbents who launch "AI features" on day 1.
4. **Compliance posture is a moat, not a tax**: Amazon's March 2026 AI Agent Policy maps directly onto our HITL architecture. When Walmart and eBay publish similar policies (they will), Copio is already compliant. Incumbents retrofit; Copio doesn't.

### Phase 2 buyer pool — strategic question

Phase 2 expands the addressable buyer in two distinct ways. Need to decide which is the primary motion before Phase 2 ships:

| Motion | Buyer | Acquisition path |
|---|---|---|
| **Expansion** (compounds) | Phase 1 customer (Amazon-native CEO) who decides to add Walmart/Shopify/eBay during Copio's lifetime with them | In-product upsell, no new GTM |
| **Acquisition** (TAM unlock) | Multichannel CEO who didn't need diagnostic agent alone but does need channel-sprawl management | Net-new GTM motion: positioning, ad spend, content |

Recommendation: **lead with expansion**. It compounds on Phase 1 trust, requires no new GTM, and produces the strongest customer testimonials ("I was on Amazon only; Copio walked me into Walmart in a week"). Acquisition motion gets unlocked organically once expansion case studies exist.

**Open question for /plan-eng-review:** does Phase 2 need its own architecture-review pass, or does the Phase 1.1 architecture absorb it cleanly? Tentative answer: the Phase 1.6 HITL infrastructure + per-channel adapters is straightforward, but the **catalog-attribute-mapping engine** (Amazon attributes → Walmart/Shopify/eBay schemas) is non-trivial and deserves its own review.

**Reversibility**: 4/5. Every phase is built on the prior; rollback to a prior phase is feasible. The only genuinely one-way decision is multi-tenancy from day 1, which is justified by avoiding a painful retrofit.

**Path dependency**: real. The eval rig + honest voice + memory together create a compounding moat. Skip any one and the brand promise breaks; skip the eval rig and "self-improving" is theater.

### Prompt caching architecture

Per [Anthropic prompt caching guidance, 2026](https://platform.claude.com/docs/en/build-with-claude/prompt-caching) and [explicit-vs-auto guidance](https://www.mager.co/blog/2026-04-29-claude-prompt-caching/):

- **4 explicit cache breakpoints** per request (max allowed by Anthropic API)
- **Cached static prefix**: tool definitions → persona voice doc → system prompt → tenant memory snapshot
- **Dynamic suffix (not cached)**: current question + retrieved per-question context
- **Eval rig must verify cache-hit-rate ≥ 80%**; misplaced breakpoint silently degrades to full-price call
- Workspace-level isolation (Anthropic Feb 2026 change) — each tenant gets its own workspace key for cache isolation

**Untranslatable-attribute handling** (REQUIRED — flagged in eng review):

- Escalation: agent surfaces "Can't replicate X to Walmart for SKU-A. Use closest equivalent (suggested), omit, or override?"
- Decision memory: persisted per-(tenant, source-channel-pair, category, attribute) so future SKUs in same category replicate without re-asking

### Per-tenant cost budget enforcement

**Graceful degradation chosen** (warn at 80%, escalate at 100%):
- Tracked: daily LLM spend + daily SP-API call count + daily report-poll count per tenant
- 80% warning: agent surfaces *"I'm approaching today's budget; should we be selective?"* — honest-voice fits naturally
- 100% reached: refuse new diagnostics until next period; admin override available
- Daily/monthly budget configurable per tenant tier
- Budget enforcement is on the runtime path (hard gate), not just an alert

## Reviewer Concerns (from spec review loop, persisted)

These items were raised by adversarial review and are not fixed in the plan — preserved here so downstream skills + future readers see them:

- **Pricing is unvalidated.** $199-499/mo is a vibes claim until the $50 waitlist deposit experiment runs. Treat as hypothesis, not fact.
- **Cross-tenant contamination eval has limits.** Sentinel-string probes catch identifier leaks but are weak against semantic leaks ("I notice your competitor is doing X" where competitor info actually came from tenant B's data). The unit test on the prompt builder is the real defense; the contamination eval is a backstop. Do not over-rely on the nightly probe.
- **First-diagnostic latency promise depends on report scope.** "First useful diagnostic in <60 min" is realistic for Orders + FBA inventory questions; deeper diagnostics against Brand Analytics / SQP take 4-24h depending on the report types requested. Onboarding UX must explain this clearly so the first impression isn't broken.
- **Slack reaction → eval pipeline doesn't exist on web chat without custom UI.** Phase 1.1 web chat needs an explicit thumbs/emoji widget on each diagnostic + a free-text "tell me what was wrong" input. Mapping: 👍 = positive gold-standard; 👎 = flag for review; 🎯 = exactly right; ❓ = unclear; 🔁 = wrong, retry. Defer Slack-native reactions to Phase 1.5.
- **"Self-improving" is operationally defined as eval-guided prompt iteration with humans in the loop**, not runtime learning. Be honest about this in marketing copy or the brand promise frays.
- **The 4-5 day Phase 1.0 still depends on the founder's golden-question authoring being complete.** If that's not done in parallel, Phase 1.0 ships without an eval foundation and the brand promise of "real eval rig from day 1" only really kicks in in Phase 1.1.
